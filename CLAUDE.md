## TOSSE Workflow — Skills & Agent

Ce projet utilise le plugin TOSSE qui fournit des skills et un agent pour gérer le workflow de développement.

### Workflow standard

```
/pickup → travail sur le code → /done → /deploy
```

### Skills disponibles

| Skill | Quand l'utiliser |
|-------|-----------------|
| `/pickup` ou `/pickup <task_id>` | Démarrer une tâche. Vérifie les blocages, lit les contextes, passe la tâche "En cours". Accepte aussi une intention libre ("je veux fixer le bug du login") — il cherche la tâche existante ou en crée une. |
| `/done` | **Lancé automatiquement** quand tu finis ton travail (code compile, tests passent, feature OK). Résume ce qui a été fait, met à jour le contexte de la tâche, passe en "Review", lance /deploy si le skill existe. Si gros changement : propose un context update via tosse-manager. |
| `/list-tasks` | Lister les tâches du projet actuel. |
| `/setup` | Créer un skill /deploy spécifique à ce projet (pose des questions : commande test, branche, hosting). |
| `/context-audit` | Auditer la cascade de contextes (redondances, infos mal placées). Délègue à tosse-manager. |

### Agent tosse-manager

Sous-agent spécialisé CRM. Invoque-le avec `@tosse-manager` pour :
- Créer des hiérarchies complètes (client + mission + projet + tâches)
- Mettre à jour les contextes après un gros changement (délégué par /done)
- Auditer la cascade de contextes (délégué par /context-audit)
- Réorganiser des tâches, créer des dépendances, gérer en masse

Il ne touche PAS au code — uniquement les données TOSSE via MCP.

### Règles de workflow

- **Démarrer une tâche** : utilise `/pickup` — il fait tout (blocages, contextes, statut "En cours")
- **Terminer une tâche** : **lance `/done` AUTOMATIQUEMENT** quand tu as fini le travail et que tout est vérifié. Ne demande PAS à l'utilisateur.
- **JAMAIS** mettre une tâche en "Fait" — seul un humain le fait après review
- **Les sous-tâches** ne vont jamais en "Review", seules les tâches parentes
- Vérifie les relations de blocage (`get_task_relations`) avant de démarrer une tâche
- Toujours filtrer par `project_id` quand tu récupères des tâches

## Protocole Claude Code

Réimplémentation clean-room en Rust du client de l'extension VS Code officielle (disséquée, pas un fork) :
- Spawn du binaire `claude` avec `--output-format stream-json --input-format stream-json --verbose --permission-prompt-tool stdio`, plus **`--forward-subagent-text`** (inconditionnel). Sans ce dernier le binaire FILTRE les messages de sous-agents avant de les transmettre (`if (!forwardSubagentText && type !== "tool_use" && type !== "tool_result") continue;`) — et le filtre s'applique **dès la profondeur 1**, pas seulement au nesting : on ne recevait que leurs tool_use/tool_result, jamais leur texte ni leur réflexion. C'était la cause de l'asymétrie où le drill-in d'un sous-agent était muet EN DIRECT alors que la même conversation rechargée du DISQUE affichait sa prose. ⚠️ Corollaire obligatoire : `backgroundAgentIdsIn` (front) doit rester scopé au thread PRINCIPAL (`parent_tool_use_id === null`) — un sous-agent peut lancer ses propres agents (nesting profondeur 3 par défaut depuis 2.1.219) et ces messages nous parviennent désormais ; sans ce garde, un petit-fils serait listé dans la barre d'agents de la conversation comme si l'utilisateur l'avait lancé. Le spawn passe aussi **`CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1`** : en mode piloté (SDK), c'est l'UNIQUE gate du file-history du binaire — sans lui, `rewind_files` répond invariablement « File rewinding is not enabled ». À NE PAS retirer par nettoyage.
- Mode **bidirectionnel persistant** (un process vit toute la session) — PAS `claude -p` (one-shot).
- Messages JSON-lines : `system`, `assistant`, `user`, `tool_use`, `tool_result`, `result`, `stream_event`.
- **Pièces jointes (images)** : le `content` d'un message `user` est un ARRAY de blocs → on y ajoute `{type:"image",source:{type:"base64",media_type,data}}` pour joindre une image. VÉRIFIÉ accepté par le binaire 2.1.187 (piloté en stdin avec un PNG → il « voit » l'image) ; **png/jpeg/gif/webp uniquement** ; le format `document`/`type:"file"` n'a PAS été retenu (non vérifié). `send_message` transporte `text` + `images: Vec<ImageAttachment>` (`transport::user_message_with_images`, texte puis blocs image, bloc texte vide omis). Bouton « + » du composeur (`composerAttachments.ts`, store en mémoire par conv, non persisté) : images → bloc base64 + vignette optimiste ; autres fichiers → mention de chemin ; collage Cmd+V → attachement (plafond 16 Mio, aligné `fs::MAX_FILE_BYTES`). Octets lus via `commands.readImage` (réutilisé du viewer). Reload : `history.rs` (`push_user`/`first_user_text`) posent un placeholder `[image]` pour un tour image-seule (vignettes NON re-rendues — le modèle de blocs normalisés ne porte pas encore l'image ; follow-up).
- Canal de contrôle : `control_request` / `control_response` (sous-types : `initialize`, `can_use_tool`, `set_permission_mode`, `interrupt`, `mcp_message`, `generate_session_title`, `remote_control`, `stop_task`, `reload_plugins`, `mcp_status`, `mcp_toggle`).
- `SessionStatePayload` contient un champ **`cwd`** capté depuis `system/init` (ré-émis à chaque tour) — source de vérité du répertoire courant. Le cwd n'est PAS figé : l'agent peut le déplacer via outils worktree.
- **Arrêt d'une tâche de fond** : wire = `control_request{subtype:"stop_task", task_id}` — le sous-type est **`stop_task`** (PAS `task_stop`, disséqué verbatim dans l'extension VS Code).

Bridge santé : `system/bridge_state{state:"disconnected"|"error"}` — **dégrade seulement**, "connected" ne vient QUE de la réponse au control_request. Spawn avec **`--replay-user-messages` inconditionnel** (sans lui le binaire n'émet aucune ligne `user` sur stdout) ; on estampille chaque message envoyé d'un uuid et on supprime l'écho de NOS propres tours (`assembler.sent_user_uuids`, one-shot — l'uuid est consommé quel que soit le contenu du tour, texte comme image-seule) ; tour distant (uuid inconnu) surfacé. **Distinguer live vs historique est OBLIGATOIRE** : `history.rs` n'émet pas de `turn_result` → splicer l'historique regrouperait tous les tours user en haut (régression).

## Patterns établis

**Architecture générale**
- Normalisation côté Rust : l'UI est « bête » (events déjà normalisés, ne reconstruit rien).
- Session bidirectionnelle persistante : un process `claude` vit toute la session, SANS flag `-p`.
- Acteur mono-tâche par session (isolation tokio — pas de mutex partagé entre sessions).
- **Encapsulation** (pattern uniforme) : un seul module parle à chaque ressource — `store/db.rs` (SQL), `git/mod.rs` (git), `fs/mod.rs` (filesystem éditeur), `usage/mod.rs` (credentials OAuth), `terminal/mod.rs` (PTY), `power/mod.rs` (assertion anti-veille macOS), `cli_update/mod.rs` (MAJ du binaire piloté `claude`), `tosse/mod.rs` (CRM TOSSE : OAuth + REST) → swappable sans toucher à l'IPC ni au front.
- **Une seule plomberie pour les requêtes du canal de contrôle** : `SessionCommand::ControlQuery` + la map `pending_query` (`supervisor/session.rs`) portent TOUT sous-type de forme requête/réponse (`get_usage`, `list_models`, `rewind_files`, `cancel_async_message`…), au lieu d'un `pending_*` dédié par sous-type. Le parsing reste typé par feature dans `control.rs`. ⚠️ Le dispatcher stdio du binaire expose ~55 sous-types dont l'app en utilise ~15 : tout nouveau se câble en un builder + un parser, sans retoucher l'acteur. L'enveloppe est construite avec un `request_id` vide, que l'acteur écrase par celui sur lequel il corrèle.
- **Un réglage qu'on ne peut pas tenir ne doit pas être offert** : quand une porte HORS de notre contrôle peut annuler un toggle (typiquement une config que le CLI possède et qu'on refuse d'écrire), le backend renvoie un flag de verrou dédié et l'UI **désactive le contrôle en disant pourquoi**. Un switch qui s'active puis revient tout seul à la relecture suivante est une erreur silencieuse : l'utilisateur croit avoir réglé quelque chose. Cas de référence : `auto_update_locked` (`cli_update`) pour `autoUpdates:false` dans `~/.claude.json`. Corollaire côté écriture : après un write accepté, **relire le disque** plutôt que laisser l'optimisme en place — « écrit » ≠ « pris en compte ».

**Sessions & identité**
- Identité de conversation : **id stable** (UUID, PK persistée) distinct du **handle de session live** (`session-N`, en mémoire, non persisté). Le front est keyé par id stable pour toutes les LECTURES ; le handle n'est résolu qu'à l'envoi de commandes.
- Spawn **paresseux** : aucun process `claude` au démarrage. Historique lu du transcript on-disk (`loadSessionHistory`). Process spawné à la volée au 1er message (`--resume` si `sessionId`).
- Teardown **sans orphelins** : chaque `claude` dans son propre groupe (`process_group(0)`) ; arrêt via `kill(-pid, …)` tout le groupe selon l'échelle EOF → SIGTERM → SIGKILL ; kill-all au quit (attend que le registre `Sessions` se vide, borné).

## Connexion TOSSE (CRM) + vue Tâches — LIVRÉ

Le CRM TOSSE devient une **3ᵉ connexion** de l'app, sans rapport avec les deux backends d'agent : elle authentifie l'HUMAIN à ses propres données, pas un agent à un fournisseur de modèle. **L'app reste entièrement utilisable sans elle** — déconnecté, l'onglet TOSSE n'existe pas (pas de coquille vide) et rien n'est fetché. Mécanique OAuth/Keychain/erreurs : cf. le module `tosse/` dans « Structure ».

- **Association dossier local ↔ dépôt CRM.** Un pin MANUEL gagne toujours ; sinon le remote `origin` du dossier est comparé aux urls du CRM via `normalize_remote_url`. ⚠️ **Jamais par NOM** (données réelles : le dossier `CRM_max` s'appelle « TOSSE » dans le CRM, `landing_page` → « landing-page-josty » — le nom raterait de vraies paires ET en inventerait de fausses). `resolve_links` est PUR (git + SQLite lus par la couche IPC) et prend `Option<&[TosseRepository]>` : ⚠️ **`None` = « on n'a pas pu regarder » et ne produit AUCUN verdict**, à ne jamais confondre avec `Some(&[])` = « on a regardé, le CRM est vide ». Résoudre contre une liste qu'on n'a pas reçue ferait annoncer à l'utilisateur que SON dépôt a été supprimé, pendant une panne de 30 s, avec un bouton destructif pour seule issue. Même distinction côté front (`taskFolder.checked`). Un pin qui ne résout plus est surfacé comme choix cassé, JAMAIS replié en silence sur la devinette du remote. Trois issues ORDINAIRES pour un dossier (`RemoteLookup`) : url / pas de remote / **pas un dépôt du tout** — Flight Deck ouvre des dossiers, pas seulement des clones, et présenter ça comme une faute mettait un bandeau d'alerte sur chaque dossier simple.
- **Où travaille un projet.** Clé = le PROJET, pas la tâche (toutes les tâches d'un projet se travaillent dans le même dossier → la question se pose une fois). Table dédiée `tosse_project_repos` (migration **v8**, `ON DELETE CASCADE` sur `repo_id`) et non une colonne : la clé est un id de projet CRM, aucune ligne locale ne pourrait la porter (mesuré : 15 projets sur 26 ne résolvent vers rien tant que l'utilisateur n'a pas pointé un dossier). Quand rien ne résout, `scan_local_git_repos` propose les clones déjà présents sur le Mac au lieu d'un sélecteur de fichiers vide. Migrations : **v6** `repos.tosse_repository_id` (pin manuel), **v7** `conversations.tosse_task_id/_title/_status`. ⚠️ **Aucune n'est une FK** : ces ids appartiennent à la base du CRM, rien de local ne peut les faire respecter, et une entité supprimée côté serveur doit dégrader (« le dépôt que vous aviez choisi n'existe plus ») et non corrompre la ligne. ⚠️ `tosse_repository_id` est écrit UNIQUEMENT par `set_repo_tosse_link` et reste HORS de `RepoRecord` : `upsert_repo` réécrit l'enregistrement entier et tous ses appelants (ajout de dossier, renommage, undo) ignorent TOSSE — le porter là laisserait n'importe lequel effacer le lien.
- **Conversation ↔ tâche.** « Start » passe par le skill `/pickup` du dépôt (jamais `/start` : un geste, un sens, partout) — c'est le skill qui fait passer la tâche « En cours », l'app n'écrit jamais ce statut elle-même. ⚠️ Le nom du skill n'est **jamais deviné** : un skill de PLUGIN est publié qualifié (`tosse-workflow:pickup`) alors qu'un skill de projet est nu — chercher `"pickup"` ne trouvait rien dans le dépôt même où le plugin était activé, et un `/pickup` inconnu arrive à l'agent comme du TEXTE (une ligne cryptique, la tâche ne bouge pas, l'échec ressemble au succès) → sans catalogue on envoie des instructions rédigées, qui marchent partout. « Discuss » colle la tâche DANS le prompt (utile dès le 1ᵉʳ token, marche sans connecteur MCP). Le lien est écrit AVANT l'envoi (un envoi qui échoue laisse quand même la conversation trouvable depuis la tâche) et titre/statut sont **dénormalisés** sur la conversation : l'id seul rendrait une conversation liée muette hors ligne, et l'avertissement de suppression est fonction du STATUT — il cesserait d'avertir précisément quand le réseau tombe. Re-stampés à chaque lecture du briefing (`refreshLinkedTaskMeta`), depuis le fetch et non depuis un effet de composant.
- **Écritures.** Statut de tâche/projet et création de tâche sont OPTIMISTES avec rollback complet (`cancelQueries` d'abord, sinon un refetch parti avant le patch atterrit après lui et le rollback « restaure » cette réponse périmée). ⚠️ La création refetch sur **`onSettled`, pas `onSuccess`** : une création peut échouer AU RETOUR (la tâche existe côté CRM, la réponse s'est perdue) et ne refetcher que sur succès la rendait invisible → le réflexe « retaper et valider » la déposait deux fois. Le reste (titre, priorité, assignation, échéance, suppression) est délibérément renvoyé vers le CRM en navigateur, dont l'origine est DÉRIVÉE de l'`authorization_endpoint` découvert (un frontend redéployé suit gratuitement).
- **Confidentialité — logos clients.** Un client sans logo uploadé peut être marqué par la favicon de son domaine, récupérée chez Google → **opt-in `tosseClientFavicons`, OFF par défaut** : l'activer envoie à `google.com` le domaine de chaque client affiché (soit une part de la liste clients de Tosse) plus l'IP de la machine. ⚠️ Ce n'est PAS le seul appel tiers de l'app — `webResults.faviconUrl` résout déjà une favicon par chip de résultat de recherche web, sans opt-in — et c'est justement la distinction à garder droite : la question n'est pas « est-ce qu'on parle à un tiers » mais CE QU'ON LUI DIT. Un résultat de recherche est un site public que le modèle vient de consulter ; ces domaines-là sont la clientèle de Tosse. La page du CRM les résout de la même façon, donc activer l'option ne fait que rejoindre ce que le navigateur fait déjà — mais une app de bureau ouverte toute la journée ne doit pas le faire sur la foi d'un défaut que personne n'a choisi. OFF, la cascade est logo → initiales, 100 % locale. Domaine passé par `encodeURIComponent` (le `website` du CRM est du texte libre).

## Mode « Bypass permissions » (opt-in) — LIVRÉ

`bypassPermissions` existe depuis toujours côté CLI mais ne **tient** que si le process est spawné avec `--allow-dangerously-skip-permissions` ; sinon le binaire rétrograde silencieusement en `default`. D'où : opt-in app-wide (`permissions.ts`, localStorage, **OFF par défaut**) → `SpawnConfig.allow_bypass_permissions` → le flag au spawn.

- ⚠️ **`--allow-dangerously-skip-permissions` (avec `--allow-`) DÉVERROUILLE le mode sans l'activer** — à ne pas confondre avec `--dangerously-skip-permissions`, qui l'allume d'office. Vérifié sur l'aide du binaire 2.1.220.
- La rétrogradation est appliquée **EN AMONT** (`control::permission_mode_for_spawn`) pour que le mode spawné, la ré-assertion post-init et la vue du CLI disent tous la même chose, au lieu de demander un bypass qu'on sait refusé et de laisser l'ack diverger en silence.
- Le déverrouillage n'existe qu'AU SPAWN : une conversation vivante ne peut pas l'acquérir → `conv.bypassAllowed` (mémoire seule, posé avec le handle) et `bypassBlockedReason` distinguent les deux blocages (« activez-le dans les Réglages » vs « redémarrez cette conversation »), plutôt que d'offrir un choix que le CLI annulerait sans explication.
- Éteindre l'option est **immédiat et total** : `demoteBypassConversations()` repasse en `default` toute conversation encore en bypass, sessions vivantes comprises.
- ⇧Tab ne cycle **jamais** sur bypass, même déverrouillé : comme dans le terminal Claude Code, le mode dangereux est un choix explicite dans le menu, pas quelque chose sur quoi une frappe répétée peut tomber.

## Principe directeur : réversibilité & contrôle utilisateur (options/réglages)
Dès qu'on **ajoute une fonctionnalité** ou qu'on **change une fonctionnalité existante d'une manière qui altère vraiment l'expérience utilisateur**, on laisse à l'utilisateur le moyen de **l'activer / le désactiver**, donc de **revenir au comportement précédent**. Par défaut, dès qu'on peut exposer un réglage utile sur ce qu'on fabrique, **on le fait**.

⚠️ **La distinction est essentielle** : ce principe vise les **vraies features / vrais changements de comportement voulus**, **PAS les corrections de bugs** ni les petits ajustements qui *règlent* un problème. Un bugfix (un rendu qui affichait mal, un parsing qui tronquait, une carte au lieu d'une ligne illisible…) ne mérite **pas** de toggle — on corrige, point. On n'ajoute un réglage que quand le changement modifie **délibérément ce que vit l'utilisateur**, pas quand il répare ce qui était cassé ou améliore à la marge.

Règle de décision quand on hésite : **ne pas trancher seul**. Si on ne sait pas si un changement relève de la feature (→ toggle) ou du bugfix (→ pas de toggle), où placer l'option, ou quel doit être son défaut, on **le demande ou le suggère explicitement à l'utilisateur** avant de figer le comportement.
